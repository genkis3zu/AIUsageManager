# AI の使用量の共有ファイル（仕様 第 1 版）

- 日付: 2026-11-28
- 状態: 確定（2026-11-28、Commander がこの内容のまま AIUsageManager 側に渡し、実装を始めた）
- この仕様を実装するアプリ:
  - Input Assistant for AI Agents（VS Code 拡張、このリポジトリ）
  - AIUsageManager（Windows のトレイアプリ ＋ Stream Deck プラグイン、`D:\Dev\AIUsageManager`）
- この文書だけを読めば実装できるように書いてある。相手のアプリのコードを読む必要はない。

## 1. 何のための仕様か

2 つのアプリは、どちらも同じ PC で、同じログイン情報を使って、同じ取得先から AI の使用量を 5 分ごとに取得している。

| 名前 | 取得先 |
|---|---|
| `claude` | `GET https://api.anthropic.com/api/oauth/usage` |
| `codex` | `GET https://chatgpt.com/backend-api/wham/usage` |

これらの取得先は、短い間隔で続けて呼ぶと取得制限（HTTP 429）を返す。Claude の取得先は、2026-09-21 の実測で「成功 → 約 3 分間は 429 → 成功」だった。2 つのアプリが別々に 5 分ごとに呼ぶと、あとから呼んだほうが 429 になり、古い値や「取得制限中」の表示になる。

この仕様は、**取得した結果と「いつまで呼ばないか」を、どちらのアプリのものでもない場所に置き、呼ぶ前にそこを見る**ことで、同じ PC の中での呼び出しを 1 つにまとめる。

守ること:

- 2 つのアプリは独立したままにする。相手が入っていなくても、今までどおり動く。
- それぞれが自分用に保存しているもの（Input Assistant の `~/.input-assistant/usage-cache.json`、AIUsageManager が読む `~/.claude/usage-cache.json` など）は、この仕様では変えない。
- 共有の場所が無い・読めない・壊れているときは、無いものとして扱い、今までどおり自分で取得する。共有の場所が原因でアプリが止まったり、エラーを出したりしない。
- ログイン情報（トークンなど）は共有の場所に書かない。

## 2. 共有の場所

フォルダー: `<ホーム>/.ai-usage-shared/`

- `<ホーム>` は、OS のユーザーのホームフォルダー（Windows では `%USERPROFILE%`、Node では `os.homedir()`、.NET では `Environment.GetFolderPath(Environment.SpecialFolder.UserProfile)`）。
- フォルダーが無ければ、書くときに作る。読むだけのときは作らない。
- macOS / Linux では、フォルダーを 0700、ファイルを 0600 で作る。Windows では既定のままでよい。

ファイル（取得先ごとに 2 つ。`<名前>` は上の表の `claude` / `codex`）:

| ファイル | 中身 | いつ書くか |
|---|---|---|
| `<名前>.json` | 最後に成功した取得の結果 | 取得に成功したとき |
| `<名前>.rate-limit.json` | 「この時刻までは呼ばない」 | 取得制限（HTTP 429）を受けたとき |

2 つに分けてあるのは、どちらも「丸ごと置き換える」だけで済むようにするため（読んでから書き戻す処理をしない。2 つのアプリが同時に書いても、相手の書いた別の種類の情報を消さない）。

`README.txt`: フォルダーを作ったアプリが、次の内容で置く（すでにあれば何もしない）。フォルダーを見つけた利用者が、何のフォルダーか分かるようにするため。

```
This folder is shared by apps that show AI usage (for example "Input Assistant for AI Agents"
for VS Code and "AIUsageManager"). Each app writes the usage it fetched here so that the other
apps on this PC can reuse it instead of calling the same service again.
It contains usage numbers and reset times only. No login information is stored here.
It is safe to delete this folder at any time; the apps will create it again.
```

## 3. ファイルの形

文字コードは UTF-8（BOM なし）。JSON のオブジェクト 1 つ。時刻はすべて UTC の ISO 8601 の文字列。**書くときは、常にミリ秒つきで末尾を `Z` にする**（例 `2026-11-28T10:41:05.239Z`）。読むときは、時刻として読める ISO 8601 の文字列なら受け付ける。数値の時刻は受け付けない。

### 3.1 `<名前>.json`（最後に成功した取得の結果）

```json
{
  "version": 1,
  "provider": "claude",
  "fetchedAt": "2026-11-28T10:41:05.239Z",
  "writer": "input-assistant-vscode/2.0.1",
  "body": { "…": "取得先が返した JSON をそのまま" }
}
```

| 鍵 | 型 | 意味 |
|---|---|---|
| `version` | 数値 | この仕様の版。`1` |
| `provider` | 文字列 | ファイル名の `<名前>` と同じ値 |
| `fetchedAt` | 文字列 | 取得先から成功の応答（HTTP 200）を受け取った時刻 |
| `writer` | 文字列 | 書いたアプリの名前と版（`<アプリの名前>/<版>`）。調べるときの手がかり用で、読む側は動作を変えない |
| `body` | オブジェクト | 取得先が返した JSON。**解釈した結果ではなく、応答そのもの**を入れる（アプリごとに読み方が違うため）。ただし 3.3 の鍵は取り除く |

### 3.2 `<名前>.rate-limit.json`（この時刻までは呼ばない）

```json
{
  "version": 1,
  "provider": "claude",
  "observedAt": "2026-11-28T10:44:10.000Z",
  "until": "2026-11-28T10:49:10.000Z",
  "writer": "ai-usage-manager/1.4.0"
}
```

| 鍵 | 型 | 意味 |
|---|---|---|
| `version` / `provider` / `writer` | | 3.1 と同じ |
| `observedAt` | 文字列 | HTTP 429 を受け取った時刻 |
| `until` | 文字列 | この時刻までは、どのアプリもこの取得先を呼ばない |

`until` の決め方: 応答に `Retry-After` があればそれに従う。無ければ `observedAt` の 5 分後。どちらの場合も、`observedAt` の 3 分後より早くしない。`observedAt` の 60 分後より遅くしない。

### 3.3 `body` から取り除く鍵

書く前に、`body` の中（入れ子を含む）から、名前が次のどれかの鍵を取り除く: `email`、`user_id`、`account_id`。使用量の表示に要らず、本人を特定できるため。ほかの鍵はそのまま残す。

## 4. 書くときの決まり

1. **丸ごと置き換える。** 同じフォルダーの中に一時ファイル（例 `claude.json.<プロセス ID>.tmp`）を書き、そのあと目的の名前に置き換える（Node は `fs.renameSync`、.NET は `File.Replace` か、置き換えを指定した `File.Move`）。書きかけのファイルを相手に読ませないため。置き換えに失敗したら、一時ファイルを消して諦める（次の取得でまた書く）。
2. **成功したら `<名前>.json` を書く。** HTTP 200 で、応答が JSON のオブジェクトとして読めたときだけ。応答を自分のアプリで解釈できたかどうかは問わない。
3. **HTTP 429 を受けたら `<名前>.rate-limit.json` を書く。** `<名前>.json` には触らない。
4. **それ以外の失敗では何も書かない。** 401（ログインが必要）、403、通信の失敗、タイムアウトなど。
5. **共有ファイルから得た結果を、書き戻さない。** 自分で取得先を呼んで得た結果だけを書く（`fetchedAt` が書き換わって、古い結果が新しく見えるのを防ぐ）。
6. 書けなかったとき（権限が無い、ディスクがいっぱい、など）は、取得した結果の表示は普通に行う。ログを残す仕組みがあるアプリは、ログに 1 行残す（仕組みが無いアプリは残さなくてよい）。

## 5. 呼ぶ前の決まり

**ログイン情報が無い・期限が切れているときは、この手順に入らない。** 共有の場所は見ずに、今までどおり「ログインが必要」などの表示にする（ログアウトしているのに、ほかのアプリが取得した値が出るのを防ぐ）。

取得先を呼ぶ前に、毎回この順で確かめる。以下の「最後に成功した取得の時刻」は、**`<名前>.json` の `fetchedAt` と、自分が持っている最後の結果の時刻のうち、新しいほう**を指す（共有の場所に書けている間は `fetchedAt` と同じ。書けないときにだけ違いが出る）。

1. **`<名前>.json` を読む。** 読めたかどうかにかかわらず、「最後に成功した取得の時刻」からの経過が「再利用の上限」より短ければ、**呼ばない**。表示は、`<名前>.json`（6 節の検査に通ったもの）と自分が持っている最後の結果のうち、新しいほうを使う。
2. **`<名前>.rate-limit.json` を読む。** 読めて、`until` が今より先で、かつ「最後に成功した取得の時刻」が `observedAt` より前（または成功した取得が 1 つも無い）なら、**呼ばない**。表示は 1 と同じく新しいほうを使う。`until` を過ぎたら、もう一度この手順を最初から行う（専用のタイマーは必須ではない。次の定期的な取得のときでよい）。
3. どちらにも当たらなければ、取得先を呼ぶ。結果は 4 節のとおりに書く。
4. **呼んで HTTP 429 を受けたとき**は、4 節のとおりに `<名前>.rate-limit.json` を書き、その回のうちに、`<名前>.json` と自分が持っている最後の結果のうち新しいほうを表示する（次の回まで待たない）。どちらも無いときだけ「取得制限中」のような表示にする。

「再利用の上限」:

- 定期的な取得のとき: 自分の取得の間隔から 30 秒を引いた値。ただし 180 秒より短くしない。（間隔が 5 分なら 270 秒）
- 利用者が手で「更新」を押したとき: 180 秒。（180 秒以内に誰かが取得していれば、呼んでも 429 になる見込みが高いので、その結果を見せる）
- 「手で更新」に入れるもの: 更新のボタンやキー、メニューの「更新」、ほかのアプリから頼まれた更新、ログインし直した直後の取得。**起動した直後の 1 回目の取得は、定期的な取得として扱う。**

表示の決まり:

- 共有ファイルの結果を使ったときも、表示する「取得した時刻」は `fetchedAt` にする（自分が読んだ時刻にしない）。
- 自分が持っている最後の結果より `fetchedAt` が古い共有ファイルは使わない。

こうすると、2 つのアプリが動いているとき、先に間隔が来たほうが取得先を呼び、もう片方はその結果を使う。取得先への呼び出しは、合わせて 1 つのアプリの分と同じ回数になる。

2 つのアプリがほぼ同時に手順を始めた場合は、両方が呼んで片方が 429 になることがある。そのときは 429 を受けたほうが `<名前>.rate-limit.json` を書き、次の手順で相手の成功した結果（`<名前>.json`）を使う。これは起きてよい。

## 6. 読んだものの検査

共有ファイルは、ほかのアプリが書いたもの・利用者が手で書き換えたものかもしれない。次のどれかに当たるファイルは、**無いものとして扱う**（エラーにしない。ログを残す仕組みがあるアプリは、同じ理由のログを繰り返さない）。

- ファイルが無い、開けない、1 MB を超える。
- JSON のオブジェクトとして読めない。（開けなかった・読めなかったときは、50 ミリ秒ほど待って 1 回だけ読み直す。相手が置き換えている最中のことがある。1 MB を超えるときは読み直さない）
- `version` が `1` でない。
- `provider` がファイル名の `<名前>` と違う。
- 時刻の鍵（`fetchedAt`、`observedAt`、`until`）が文字列でない、時刻として読めない。
- `fetchedAt` または `observedAt` が、今より 60 秒を超えて先。（時計のずれか、手で書き換えられたもの）
- `<名前>.json` の `body` がオブジェクトでない。

例外が 1 つある。`<名前>.rate-limit.json` の `until` が `observedAt` の 60 分後より先のときは、無いものとはせず、**`until` を `observedAt` の 60 分後として扱う**（両方のアプリで同じにする。片方が呼び、片方が待つ、という食い違いを防ぐ）。

`body` の中身は、自分のアプリの今までの読み方でそのまま解釈する。

**検査には通るが、`body` を自分のアプリでは解釈できないとき**（例: 取得先が応答の形を変え、相手のアプリは新しい形を読めるが、自分は読めない）:

- その `<名前>.json` の `fetchedAt` は、5 節の「最後に成功した取得の時刻」に入れる（手順 1 と 2 のどちらでも）。つまり、新しければ呼ばない。`body` は同じログインで取得先が返した応答そのものなので、自分で呼んでも同じ応答が返る見込みが高く、呼べば 429 になりやすいため。
- 表示には、その `body` を使わない。解釈できるもの（自分が持っている最後の結果）があればそれを出す。無ければ、自分で呼んで解釈できない応答が返ったときと同じ表示にする。

## 7. 分かっている制限

- **アカウントを切り替えた直後**: 共有ファイルにはアカウントの区別が無い。ログインし直して別のアカウントになった直後は、最大で「再利用の上限」の間、前のアカウントの値が出ることがある。
- **PC の時計**: 2 つのアプリは同じ PC の時計を使う前提。時計を大きく変えた直後は、6 節の検査で共有ファイルが使われないことがある（その間は今までどおり自分で呼ぶ）。
- **WSL やリモートで動く VS Code**: 拡張が Windows と別のホームで動いているときは、共有の場所も別になり、共有されない（今までどおりの動作になる）。
- **取得先の制限の実際の長さ**: 180 秒は 2026-09-21 の 1 回の実測に基づく。変わったと分かったら、この仕様の値を改め、版を上げる。

## 9. それぞれのアプリでやること

### Input Assistant for AI Agents（このリポジトリ）

- `claude` と `codex` の取得で、5 節の手順と 4 節の書き方を入れる。今は解釈した結果だけを持っているので、取得先の応答そのもの（`body`）を取り出せるようにする。
- 今あるウィンドウ同士の共有（`~/.input-assistant/usage-cache.json`, DD-067）は残す。順番は「ウィンドウ同士の共有を見る → この仕様の共有の場所を見る → 呼ぶ」。
- `writer` は `input-assistant-vscode/<拡張の版>`。

### AIUsageManager

- `claude` と `codex` の取得で、5 節の手順と 4 節の書き方を入れる。
- 今ある「失敗したら `~/.claude/usage-cache.json` を読む」動作は残してよい。順番は「この仕様の共有の場所を見る → 呼ぶ → 失敗したら今までの代わりの読み取り」。
- Stream Deck プラグインはアプリから結果を受け取っているので、変更は要らない見込み。
- `writer` は `ai-usage-manager/<アプリの版>`。
- Grok の使用量は、今は AIUsageManager だけが取得している。この仕様の対象に入れるなら、名前 `grok`、取得先 `GET https://cli-chat-proxy.grok.com/v1/billing?format=credits` として同じ形で書く（入れなくてもよい）。

## 11. 仕様を変えるとき

- 鍵を足すだけの変更は、版を変えない。読む側は、知らない鍵を無視する。
- 鍵の意味を変える・鍵を消す・値（180 秒、30 秒、60 分など）を変えるときは、`version` を上げ、ファイル名はそのままにする。古い版のアプリは、新しい版のファイルを「無いもの」として扱うので、共有されなくなるだけで壊れない。
